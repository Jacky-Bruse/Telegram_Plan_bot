# 定时提醒功能设计方案（2026-01-13）

## 背景与目标
用户希望在"添加任务"时支持解析具体提醒时间。例如：
- `今晚8点`、`今天20:00`、`周五20:00`、`周五晚上八点`、`20:00`（默认今天）

带具体时间的任务：
- 在到达该时间时发送独立提醒
- 仍会出现在 `/today`、`/week`、早晚例行清单中，并附带时间展示
- 提醒消息带 `✅ 完成` / `🗑 取消` / `🕒 修改时间` 按钮（完成/取消需要二次确认）
- 提醒时间写入数据库，重启后仍可触发
- 若提醒时间已过：拒绝该行任务创建（多行输入仅拒绝该行）

## 需求约束（明确规则）
1. **仅在添加任务时解析提醒时间**，不新增 `/remind` 类命令。
2. **已过时间的行直接拒绝创建**，其余行正常创建。纯时间输入（如 `20:00`）已过时拒绝创建，不顺延到明天。
3. **任务仍参与早晚例行与列表展示**，需要附带时间。
4. **修改时间为输入新时间**，格式与创建一致。
5. **时区基准**：一律使用用户 IANA 时区。
6. **提醒时间存储为用户本地时间**（不转 UTC）。
7. **周X规则变更**：包含今天（全局生效，影响所有任务创建，不仅限于带时间的任务）。
   - 代码修改：`_get_next_weekday` 中 `if days_ahead <= 0` 改为 `if days_ahead < 0`
   - 示例：今天周五，输入"周五 买菜"解析为今天
   - 注意：不更新 `planbot-checklist.v1.0.md`，仅在本方案中记录此变更

## 最优雅方案（推荐）— 方案 B：一条提醒=一个一次性 Job
### 核心思路
- 在 `tasks` 表新增 `reminder_at` 与 `reminder_status` 字段
- 任务创建时若解析到具体时间：
  - 写入 `reminder_at`
  - 创建 APScheduler `DateTrigger` 一次性提醒 Job（`remind_{task.id}`）
- 启动时从数据库 **重建所有未到期提醒 Job**

### 优点
- 精准触发，不需要轮询
- 和现有 `scheduler` 逻辑一致，易维护
- 重启恢复可靠

### 缺点
- 需要正确管理 Job 的创建、取消、重建

## 备选方案
### 方案 A：分钟级轮询提醒表
- 每分钟扫描 `reminder_at <= now` 的任务并推送
- **优点**：实现简单，重启恢复天然
- **缺点**：资源浪费，触发精度只有分钟级

### 方案 C：复用早晚例行批处理
- 将时间任务塞入现有晚间/早间逻辑
- **优点**：改动小
- **缺点**：无法精确到具体时间，不符合需求

## 数据模型变更
在 `tasks` 增加：
- `reminder_at`：`YYYY-MM-DD HH:MM`（用户本地时间字符串，可空）
- `reminder_status`：`pending/sent/canceled`（可空，无提醒时为空）

在 `users` 增加：
- `awaiting_reminder_time`：是否等待输入新提醒时间（Boolean）
- `awaiting_reminder_task_id`：等待修改的任务 ID（Integer，可空）

说明：`due_date` 仍保留日期字段，用于 `/today` 与 `/week` 聚合展示。

### reminder_status 状态转换规则
| 场景 | reminder_status 变更 |
|------|---------------------|
| 提醒正常触发并发送 | `pending` → `sent` |
| 提醒未到，用户点"完成" | `pending` → `canceled` |
| 提醒未到，用户点"取消任务" | `pending` → `canceled` |
| 用户点"取消提醒"（修改时间界面） | `pending` → `canceled` |

### 等待状态互斥规则
`awaiting_plans` 与 `awaiting_reminder_time` 互斥：
- 进入"修改时间"状态时，自动清除 `awaiting_plans`
- 发送 `/add` 或点击"现在录入"时，自动清除 `awaiting_reminder_time` 和 `awaiting_reminder_task_id`

## 解析规则（新增时间解析）

### 解析顺序
1. 先使用现有 `parse_date` 提取日期部分
2. 再从文本**开头位置**提取时间部分
3. 时间仅识别开头位置，中间或结尾的时间表达不解析

### 支持的时间格式
| 格式 | 示例 | 解析结果 |
|------|------|---------|
| `HH:MM` | `20:00`、`08:30` | 20:00、08:30 |
| `H:MM` | `8:00`、`9:30` | 08:00、09:30 |
| `H点` | `8点`、`20点` | 08:00、20:00 |
| `H点半` | `8点半`、`20点半` | 08:30、20:30 |
| `H:MMam/pm` | `8:00pm`、`9:30am` | 20:00、09:30 |

### 支持的中文时段词
| 时段词 | 小时范围 | 示例 | 解析结果 |
|--------|---------|------|---------|
| 凌晨 | 0-5 | `凌晨两点` | 02:00 |
| 早上/上午 | 6-11 | `早上八点`、`上午十点` | 08:00、10:00 |
| 中午 | 12 | `中午十二点` | 12:00 |
| 下午 | 13-17 | `下午三点` | 15:00 |
| 晚上 | 18-23 | `晚上八点` | 20:00 |

### 组合规则
- `今晚8点` = "今天" + "晚上8点" → 今天 20:00
- `周五20:00` = "周五" + "20:00" → 周五 20:00
- `周五晚上八点` = "周五" + "晚上八点" → 周五 20:00
- `20:00` = 无日期关键词 → 默认今天 20:00
- `今晚 买菜`（无具体时间）→ 仅作为今天的普通任务，无提醒

### 已过时间处理
- 若解析到时间并且 **当前时间已过** → 该行任务拒绝创建
- 纯时间输入（如 `20:00`）已过时直接拒绝，不顺延到明天
- 示例：今天周五 18:00，输入 `周五 10:00 开会` → 拒绝创建

### "修改时间"输入规则
- 若仅提供 `20:00` → 默认今天
- 若新时间已过 → 提示重输，保持等待输入状态

## 任务内容存储与展示

### 存储策略
- `content` 字段存储**原文**（包含时间表达）
- 展示时**动态去除**开头的日期和时间表达

### 去除规则
- 仅去除开头识别到的日期+时间表达
- 保留内容中间或结尾的时间词
- 示例：
  - 输入：`20:00 开会讨论8点的方案`
  - 存储：`20:00 开会讨论8点的方案`
  - 展示：`开会讨论8点的方案`
- 示例：
  - 输入：`明天20:00 开会`
  - 存储：`明天20:00 开会`
  - 展示：`开会`

## 调度与提醒触发

### 创建时
- 若解析出 `reminder_at`：
  - 写入 DB（本地时间字符串）
  - 注册 `DateTrigger(reminder_at)`，Job ID 为 `remind_{task.id}`

### 启动时
- `scheduler.rebuild_all_jobs()` 中新增提醒 Job 重建：
  - 仅重建 `reminder_at > now` 且 `reminder_status == pending`

### 时区变更时
- 在 `rebuild_user_jobs` 中**统一处理**提醒 Job 重建
- 遍历该用户所有 `reminder_status=pending` 的任务，重建 Job
- 提醒按新时区解释（保持"本地时间不变"）

### Job 清理时机
- 任务完成或取消时，在 `callbacks.py` 中通过 `context.bot_data['scheduler']` 获取 scheduler
- 立即调用 `scheduler.remove_job(f"remind_{task_id}")` 清理 Job
- 同时将 `reminder_status` 设为 `canceled`

### 提醒触发消息
```
⏰ 提醒：{任务内容（去除时间表达后）}
时间：{YYYY-MM-DD HH:MM}
```
按钮：`✅ 完成` / `🗑 取消` / `🕒 修改时间`
- 点击完成/取消进入二次确认（沿用现有逻辑）

### 提醒触发前置校验
- 若任务已为 `done/canceled`：不发送提醒，直接将 `reminder_status` 标记为 `canceled`

## 按钮回调协议

### 现有回调格式（复用）
```
t:<task_id>:done        # 完成（第一次点击，显示确认界面）
t:<task_id>:done:cf     # 确认完成
t:<task_id>:un          # 未完成（显示顺延按钮）
t:<task_id>:cancel      # 取消（第一次点击，显示确认界面）
t:<task_id>:cancel:cf   # 确认取消
t:<task_id>:p:<days>    # 顺延N天
t:<task_id>:back        # 返回
```

### 新增回调格式
```
t:<task_id>:edit_time     # 修改时间（进入等待输入状态）
t:<task_id>:cancel_edit   # 取消修改（退出等待输入状态，回到三键界面）
```

## 修改时间流程

### 完整流程
1. 用户点 `🕒 修改时间` 按钮
2. 设置 `awaiting_reminder_time=True`，`awaiting_reminder_task_id=task_id`
3. 清除 `awaiting_plans`（互斥）
4. 编辑消息为：
   ```
   请输入新的提醒时间
   支持格式：今晚8点 / 今天20:00 / 周五20:00 / 周五晚上八点 / 20:00
   ```
   按钮：`❌ 取消修改`

5. 用户输入新时间
6. 若新时间已过：
   - 提示：`时间已过，请重新输入`
   - 保持等待输入状态
7. 若新时间有效：
   - 更新 `reminder_at`
   - 自动同步更新 `due_date`（从新时间中提取日期）
   - 清理旧 Job，创建新 Job
   - 清除 `awaiting_reminder_time` 和 `awaiting_reminder_task_id`
   - 编辑原消息为：
     ```
     ⏰ 提醒：{任务内容}
     时间：{新的 YYYY-MM-DD HH:MM}
     ```
     按钮：`✅ 完成` / `🗑 取消` / `🕒 修改时间`

### 取消修改流程
1. 用户点 `❌ 取消修改` 按钮
2. 清除 `awaiting_reminder_time` 和 `awaiting_reminder_task_id`
3. 编辑消息回到原三键界面

## 列表展示调整
- `/today`：对含时间任务追加时间展示
  - 例：`• #1 开会讨论方案（20:00）`
- `/week`：已有日期标题，仅展示时间
  - 例：`• #1 开会讨论方案（20:00）`
- 早晚例行列表同样附带时间
- 任务内容展示需**去掉时间表达**，仅用 `reminder_at` 的时间显示

## 交互与回执文案（新增/调整）
- 时间已过（创建时）：`时间已过，未创建该任务`
- 时间已过（修改时）：`时间已过，请重新输入`
- 多行回执补充：`其中 X 条因时间已过未创建`
- 创建回执（含具体时间）：
  - `• 开会讨论方案 → 2026-01-16 20:00`

## 边界与一致性
- 重复按钮点击：返回"该任务已处理"
- 任务完成/取消后，清理提醒 Job 并标记 `reminder_status=canceled`
- 时区变更：在 `rebuild_user_jobs` 中统一重建提醒 Job

## 数据迁移
- 在 `_ensure_schema` 增加 `tasks.reminder_at`（VARCHAR(16)，可空）
- 在 `_ensure_schema` 增加 `tasks.reminder_status`（VARCHAR(16)，可空）
- 在 `_ensure_schema` 增加 `users.awaiting_reminder_time`（BOOLEAN，默认 False）
- 在 `_ensure_schema` 增加 `users.awaiting_reminder_task_id`（INTEGER，可空）

## 风险与对策
- **规则变更冲突**：周X包含今天与现有规范冲突，仅在本方案中记录，不更新 planbot-checklist.v1.0.md
- **时区偏差**：统一使用用户 IANA 时区解析与存储
- **重启漏发**：启动时重建所有未来提醒
- **回调重复**：复用 `callbacks` 去重机制
- **等待状态冲突**：两种等待状态互斥，进入一种时自动清除另一种
